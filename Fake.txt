desactiva. Efecto: el jugador parece "congelado" para los demás / lag masivo.

EFECTOS DE ALTERAR (what-if):

1) fdm_n / fdm_x (piso/techo del rango de captura):
   - Son configurables en SharedPreferences "cfg" (el APK los lee).
   - Subir fdm_n (ej. 100) -> solo se retienen paquetes de >=100 bytes; el freeze
     deja pasar los pequeños (acks, pings) -> conexión más estable, efecto menor.
   - Bajar fdm_n a 0 -> se retienen casi todos los paquetes (freeze total; riesgo
     alto de timeout/desconexión).
   - Subir fdm_x (ej. 900) -> se retienen también paquetes grandes (datos de escena),
     freeze más profundo pero más sospechoso.
   - Bajar fdm_x a < fdm_n -> el rango se invierte; deberFreezeDropPacket devuelve
     casi siempre false (la corrección L858 solo aplica al piso, el techo queda raro).
   - El +rng(10)/+rng(50) hace el rango volátil a propósito: alterar esas constantes
     cambia cuánto "baila" el rango entre paquetes.

2) El tope de 10000 paquetes del buffer (L1583/L1587):
   - Subirlo -> más memoria y un flush más masivo (ráfaga gigante al apagar;
     riesgo de ban o de que el juego se cuelgue).
   - Bajarlo -> buffer se llena antes, se descartan los más viejos (el freeze
     "pierde" cobertura, se nota menos).
   - Cada paquete reempaquetado ocupa memoria: 10000 * (IP+UDP+payload) ≈ varios MB.
     Bajarlo a 2000-3000 es lo prudente si se quiere estabilidad.

3) Sleeps del flush (L831: rng(3)+1, cada 2 paquetes):
   - Son 1-3 ms cada DOS paquetes. Muy ligero.
   - Subir a rng(10)+5 -> el flush se alarga; el "rebote" del lag se reparte más
     tiempo (menos explosivo, más sostenido).
   - Bajar a 0 -> todo se vacía en un solo write() -> pico brutal, más ban-friendly.
   - Nota: el hilo es prioridad 10 (MAX_PRIORITY): se come CPU a propósito.

4) El umbral anti-flood (L1677: 5000 ms / >4000 paquetes):
   - Bajar a 1000 ms -> se dropean antes los picos tras el flush (protege más al
     servidor/juego pero el freeze "corta" antes).
   - Subir a 20000 ms -> se deja pasar la ráfaga entera (más lag percibido).
   - Este check NO frena el flush en sí; solo descarta lo que llegue DESPUÉS.

5) El rango de puertos directos [7000,10000] (L1561/L1565):
   - El freeze NO toca el tráfico de los puertos 7000-10000 (se entrega directo).
   - Si el tráfico crítico del juego va por otro puerto, se expande el rango para
     retenerlo; si se estrecha, más paquetes pasan (freeze menos efectivo).

6) mkPkt (reempaquetado):
   - Cada paquete retenido se convierte a IP completo (header + UDP). Si se modifica
     el reempaquetado se altera qué le llega exactamente al juego en el flush.

7) Interacción con los otros modos:
   - L993: con freeze activo los paquetes de SALIDA (cliente->servidor) también
     entran en la cascada, así que el freeze NO solo retiene entrada: el envío
     normal queda condicionado. Con freeze+ghost ambos se aplican: salida limitada
     por ghost, entrada retenida por freeze.

Resumen para ajustar el modo freeze:
  - Qué se retiene: fdm_n/fdm_x (+rng) en shouldFreezeDropPacket.
  - Cuánto se retiene: tope 10000 del buffer.
  - Cómo se libera: sleeps del hilo FreezeFlush.
  - Cuándo deja de proteger: umbral anti-flood (5000 ms / 4000 paquetes).
